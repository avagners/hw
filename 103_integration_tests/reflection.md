# Интеграционные тесты: 5 примеров с числовыми значениями 7 характеристик

Материал предлагает не спорить о ярлыке «интеграционный», а измерять тест по 7 свойствам Хиллела Уэйна. Чем больше свойств имеют высокие значения, тем вероятнее тест интеграционный (семейное сходство: общей обязательной черты нет, есть ряд перекрывающихся). Ниже - 5 тестов из моих проектов (данные/бэкенд), для каждого подставлены конкретные числовые значения.

## Шкалы измерения

Чтобы числа были сопоставимы, фиксирую единицы:

1. **Выполнено строк прод-кода** - строк, покрытых тестом (по coverage), шт.
2. **Пересечено границ** - модуль/класс/слой, шт.
3. **Можно разбить на N модульных тестов** - шт.
4. **Нужно внешних сервисов** - контейнеров/эмуляторов, шт.
5. **Усилия на написание/запуск** - шкала 0-10 (0 - тривиально, 10 - дни на инфраструктуру).
6. **Нелокальность ошибки** - сколько строк в среднем просмотреть, чтобы найти причину, шт.
7. **Вероятность эмерджентности** - оценка 0-1 (вещи корректны порознь, но ломаются во взаимодействии).

## Пример 1. Репозиторий + реальная БД (PostgreSQL в testcontainers)

Тест проверяет, что загрузчик `load_users` действительно пишет строки в настоящий PostgreSQL, а не в мок.

```python
# tests/test_loader_integration.py
import pytest
from sqlalchemy import create_engine, text
from testcontainers.postgres import PostgresContainer
from app.loader import load_users

@pytest.fixture(scope="module")
def pg():
    with PostgresContainer("postgres:16") as postgres:
        engine = create_engine(postgres.get_connection_url())
        with engine.begin() as conn:
            conn.execute(text(
                "CREATE TABLE users (id int PRIMARY KEY, name text, email text)"
            ))
        yield engine

def test_load_users_writes_and_upserts(pg):
    df = make_users_df([  # 3 строки, из них одна - конфликт по id
        {"id": 1, "name": "Alice", "email": "a@x.io"},
        {"id": 2, "name": "Bob",   "email": "b@x.io"},
        {"id": 1, "name": "Alice2","email": "a2@x.io"},
    ])
    written = load_users(df, engine=pg)
    with pg.connect() as conn:
        rows = conn.execute(text(
            "SELECT id, name FROM users ORDER BY id"
        )).fetchall()
    assert written == 2
    assert rows == [(1, "Alice2"), (2, "Bob")]
```

| Характеристика | Значение | Пояснение |
|---|---:|---|
| 1. Строк прод-кода | 120 | loader + маппинг колонок + SQLAlchemy-модель |
| 2. Пересечено границ | 3 | `load_users` -> session -> psycopg -> PostgreSQL |
| 3. Можно разбить на модульных | 4 | чанкинг, построение SQL, конфликты, валидация df |
| 4. Внешних сервисов | 1 | Postgres-контейнер |
| 5. Усилия | 3 | hour-фикстура + создание схемы |
| 6. Нелокальность | 40 | нужно смотреть loader, маппинг и схему |
| 7. Эмерджентность | 0.15 | в основном типы/SQL, редко взаимодействие |

Почему интеграционный: пересекает 3 слоя и реальную СУБД, выполняется медленнее юнит-теста и падает не там, где ошибка в данных, а внутри драйвера/транзакции.

## Пример 2. HTTP-эндпоинт + БД (FastAPI + PostgreSQL)

Тест шлёт реальный HTTP-запрос в приложение и проверяет и ответ, и побочный эффект в базе (создание заказа + запись в outbox).

```python
# tests/test_orders_api_integration.py
def test_create_order_persists_and_emits_event(client, pg):
    resp = client.post("/orders/", json={"user_id": 1, "total": 1500})
    assert resp.status_code == 201
    order_id = resp.json()["id"]

    with pg.connect() as conn:
        row = conn.execute(
            text("SELECT user_id, total FROM orders WHERE id = :id"),
            {"id": order_id},
        ).one()
        event = conn.execute(
            text("SELECT payload FROM outbox WHERE topic = 'order.created'")
        ).one()

    assert row == (1, 1500)
    assert event.payload["order_id"] == order_id
```

| Характеристика | Значение | Пояснение |
|---|---:|---|
| 1. Строк прод-кода | 210 | роут + сервис + репозиторий + outbox |
| 2. Пересечено границ | 5 | HTTP -> view -> service -> repository -> ORM -> БД |
| 3. Можно разбить на модульных | 6 | валидация схемы, бизнес-правила, сериализация, запись, событие... |
| 4. Внешних сервисов | 1 | Postgres (приложение поднимается in-process через ASGI) |
| 5. Усилия | 4 | ASGI-клиент + реальная схема + outbox-таблица |
| 6. Нелокальность | 80 | ошибка может быть в схеме ответа или в SQL, искать в 4 слоях |
| 7. Эмерджентность | 0.25 | валидация + ORM + событие дают нетривиальные комбинации |

Почему интеграционный: 5 пересечённых границ и проверка побочного эффекта в БД. Внешний сервис всего один, но этого достаточно - «семейное сходство» набирается за счёт остальных свойств.

## Пример 3. Kafka-пайплайн + БД

Тест отправляет сообщение в реальный брокер, ждёт, пока потребитель его обработает, и проверяет запись в БД.

```python
# tests/test_clickstream_integration.py
def test_consumer_persists_click(kafka, pg, consumer_service):
    produce(kafka, topic="clicks", value={"user_id": 1, "url": "/home"})

    consumer_service.run_until(processed=1, timeout_s=10)

    with pg.connect() as conn:
        count = conn.execute(text("SELECT count(*) FROM clicks")).scalar()
    assert count == 1
```

| Характеристика | Значение | Пояснение |
|---|---:|---|
| 1. Строк прод-кода | 320 | producer-обёртка, consumer-цикл, десериализация, репозиторий |
| 2. Пересечено границ | 6 | Kafka -> consumer -> handler -> repository -> ORM -> БД |
| 3. Можно разбить на модульных | 8 | парсинг, роутинг, идемпотентность, запись, offset-commit... |
| 4. Внешних сервисов | 2 | Kafka + Postgres |
| 5. Усилия | 7 | testcontainers + ожидание готовности брокера + таймауты |
| 6. Нелокальность | 150 | падение может быть в producer, consumer, handler или SQL |
| 7. Эмерджентность | 0.55 | тайминги, порядок сообщений, at-least-once, дубликаты |

Почему интеграционный: два внешних сервиса, 6 границ, а основная причина нестабильности - взаимодействие во времени, которое в моках не воспроизводится (высокая эмерджентность).

## Пример 4. S3 (localstack) + ingest в БД

Тест кладёт реальный CSV в эмулированный S3, запускает ingest и сверяет число строк в витрине.

```python
# tests/test_s3_ingest_integration.py
def test_ingest_csv_from_s3(s3, pg):
    s3.put_object(
        Bucket="raw",
        Key="events/2026-09-01/part-0.csv",
        Body=make_csv_bytes(rows=1000),
    )
    run_ingest("s3://raw/events/2026-09-01/")

    with pg.connect() as conn:
        count = conn.execute(text("SELECT count(*) FROM events")).scalar()
    assert count == 1000
```

| Характеристика | Значение | Пояснение |
|---|---:|---|
| 1. Строк прод-кода | 150 | S3-клиент, парсинг CSV, pandas-трансформация, запись |
| 2. Пересечено границ | 4 | S3 -> ingest -> pandas -> БД |
| 3. Можно разбить на модульных | 5 | листинг, скачивание, разбор, нормализация, запись |
| 4. Внешних сервисов | 2 | localstack S3 + Postgres |
| 5. Усилия | 5 | поднять localstack, создать бакет, связать с БД |
| 6. Нелокальность | 60 | ошибка может быть в ключах S3, схеме CSV или SQL |
| 7. Эмерджентность | 0.20 | в основном формат/пути, предсказуемо |

Почему интеграционный: пересекает сетевую границу объектного хранилища и проверяет побочный эффект в БД; за счёт эмулятора запускается в CI, но остаётся медленнее юнит-теста.

## Пример 5. Spark-джоба -> PostgreSQL через JDBC

Тест запускает реальную (локальную) Spark-джобу, читающую parquet с диска, и проверяет агрегаты в PostgreSQL.

```python
# tests/test_daily_aggregates_integration.py
def test_daily_aggregates_written_to_postgres(spark, pg, tmp_path):
    write_parquet(tmp_path / "events", rows=10_000)

    run_daily_aggregates(
        spark,
        input_path=str(tmp_path / "events"),
        jdbc_url=pg.url,
    )

    with pg.connect() as conn:
        total = conn.execute(text("SELECT sum(clicks) FROM daily")).scalar()
    assert total == 12_345
```

| Характеристика | Значение | Пояснение |
|---|---:|---|
| 1. Строк прод-кода | 480 | Spark-джоба, UDF, схема, конфиг JDBC |
| 2. Пересечено границ | 5 | parquet -> Spark -> DataFrame-логика -> JDBC -> PostgreSQL |
| 3. Можно разбить на модульных | 7 | фильтры, агрегации, схема, запись, партиции... |
| 4. Внешних сервисов | 2 | Spark-рантайм + Postgres |
| 5. Усилия | 6 | Spark-сессия, JDBC-драйвер, volume с parquet |
| 6. Нелокальность | 200 | ошибка может быть в Spark-плане, типах или JDBC |
| 7. Эмерджентность | 0.40 | ленивые вычисления, партиционирование, сериализация |

Почему интеграционный: очень много исполняемого прод-кода и слоёв, ошибки всплывают далеко от места причины, а ленивый Spark добавляет эмерджентности.

## Выводы

Все пять тестов - интеграционные, но по разным причинам, что подтверждает «семейное сходство» из материала: общей обязательной черты нет. Пример 2 выигрывает за счёт числа пересечённых границ при одном сервисе, пример 5 - за счёт объёма исполняемого кода и нелокальности ошибок, пример 3 - за счёт эмерджентности (тайминги, порядок, at-least-once).

Числовые значения полезны именно тем, что не дают спорить о ярлыках: тест не «интеграционный» или «модульный» сам по себе, а имеет профиль по 7 шкалам. В команде такие профили я могу использовать следующим образом: если у теста растут усилия (шкала 5) и эмерджентность (шкала 7), его нужно либо изолировать (контракты, моки), либо сознательно вынести в отдельный, более медленный контур CI.
