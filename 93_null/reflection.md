# Зачем вам NULL

## Пример 1. Финансовые транзакции и скидки

Проблема: Переменная `discount = None` может означать «скидка еще не рассчитана» или «скидка равна 0%». Ошибка в коде может случайно применить None там, где важен строгий расчет.
Решение в Python: Использование паттерна `Null Object` (Нулевой объект) или явного `Decimal("0")`.

```python
from decimal import Decimal
from dataclasses import dataclass

@dataclass
class Order:
    total_amount: Decimal
    # Вместо discount: Decimal | None = None
    discount: Decimal = Decimal("0.00")  # По умолчанию скидки просто нет
```

На уровне БД: Столбец `discount DECIMAL(10, 2) NOT NULL DEFAULT 0.00`. Нам не нужен `NULL`, так как отсутствие скидки - это экономический ноль, с которым можно безопасно проводить математические операции.

## Пример 2. Даты и бесконечные периоды

Проблема: Срок действия подписки или купона. `end_date = None` часто означает «бесконечная подписка». Но None нельзя сравнивать напрямую с текущей датой без постоянных проверок `if end_date is None`.
Решение в Python: Использование специального граничного значения («Часовой дозор» / Sentinel Value), например, максимально возможной даты.

```python
from datetime import datetime

# Вместо end_date = None используем "бесконечность"
MAX_DATE = datetime(9999, 12, 31, 23, 59, 59)

def is_subscription_active(end_date: datetime) -> bool:
    # Не нужны проверки на None, работает прямое сравнение
    return datetime.now() < end_date
```

На уровне БД: `end_date TIMESTAMP NOT NULL DEFAULT '9999-12-31 23:59:59'`. Это позволяет использовать стандартные индексы и простые операторы сравнения (<=, >=) без усложнения логики базы данных.

## Пример 3. Статусы процессов и очередей

Проблема: Задача в очереди. Поле `processed_at = None` показывает, что задача еще не обработана. Из-за этого приходится писать запросы в стиле `WHERE processed_at IS NULL`.
Решение в Python: Явное управление состояниями через Стейт-машину (State).

```python
from enum import Enum
from datetime import datetime
from dataclasses import dataclass

class TaskStatus(str, Enum):
    NEW = "new"
    PROCESSING = "processing"
    COMPLETED = "completed"

@dataclass
class Task:
    status: TaskStatus = TaskStatus.NEW
    updated_at: datetime = datetime.now()
```

На уровне БД: Вместо анализа дат на `NULL`, мы вводим поле `status VARCHAR/ENUM NOT NULL`. База данных гораздо эффективнее фильтрует и индексирует конкретные текстовые или числовые статусы, чем «пустоту».

## Пример 4. Результаты поиска или коллекции данных

Проблема: Функция ищет теги пользователя. Если тегов нет, функция возвращает `None`. Это заставляет вызывающий код делать проверку: `if tags is not None: for tag in tags`
Решение в Python: Возвращать пустой контейнер (пустой список, множество или словарь) вместо `None`.

```python
# Плохо: возвращает list | None
# Хорошо: всегда возвращает list

def get_user_badges(user_id: int) -> list[str]:
    # Если в БД ничего не найдено, возвращаем пустой список
    return [] 

# Вызывающий код больше не упадет с AttributeError и не требует if-строк:
for badge in get_user_badges(42):
    print(badge)
```

На уровне БД: На высоком уровне абстракции это решается через связанные таблицы (отношение один-ко-многим). Если у пользователя нет значков, в связующей таблице просто не будет строк для его `user_id`. Нам не нужно хранить `NULL` в основной таблице.

## Пример 5. Координаты объектов на карте (Широта и Долгота)

Проблема: Приложение для трекинга курьеров или дронов. У нас есть класс `Location`. Если устройство временно потеряло связь со спутниками или еще не инициализировалось, велик соблазн выставить `latitude = None` и `longitude = None`.

Однако в коде это приведет к постоянным проверкам `if lat is not None`, а случайный пропуск такой проверки вызовет падение программы при попытке рассчитать дистанцию. В базе данных `NULL` в координатах ломает работу пространственных индексов (GiST/SP-GiST в PostgreSQL) и усложняет гео-запросы.

Решение в Python: Использование специального объекта-контейнера для валидации состояния координат или паттерна «Невалидная координата» (например, выход за границы диапазона, хотя первый вариант чище).

```python
from dataclasses import dataclass
from typing import Optional

@dataclass(frozen=True)
def GeoPoint:
    latitude: float
    longitude: float
    
    def is_valid(self) -> bool:
        # Проверяем вещественные границы координат
        return -90 <= self.latitude <= 90 and -180 <= self.longitude <= 180

@dataclass
class TelemetryData:
    device_id: int
    # Вместо хранения координат напрямую, которые могут быть None,
    # мы используем структуру, которая явно говорит, валидны ли данные
    location: Optional[GeoPoint] = None
```

На уровне СУБД эта проблема решается с помощью двух подходов:

1) Специальные типы данных (Spatial Types): В современных СУБД (например, расширение PostGIS для PostgreSQL) для координат используется специальный тип GEOMETRY или GEOGRAPHY. Вместо NULL для пустой координаты используется концепция EMPTY геометрии (например, POINT EMPTY). Она ведет себя как валидный объект, не равен NULL, но при этом СУБД четко понимает, что в нем нет точек.

2) Вынос в историческую таблицу (Логирование): Координаты - это чаще всего динамические данные. Вместо того чтобы обновлять одну строку в таблице drones и ставить туда NULL, когда дрон ушел в оффлайн, создается связанная таблица `drone_telemetry_history`. Если от дрона нет сигнала - в эту таблицу просто не записывается новая строка. Текущий статус дрона определяется по наличию или отсутствию записей за последние $N$ минут.

## Выводы

Раньше я на автомате ставил `NULL` везде, где данные казались «необязательными». Теперь я понял, что `NULL` превращает привычную булеву логику (Истина/Ложь) в трёхзначную (Истина/Ложь/Неизвестно). В SQL это приводит к коварным багам: например, когда конструкции с NOT IN внезапно возвращают пустой результат просто потому, что среди значений затесался один `NULL`. Избавление от него делает запросы предсказуемыми.

`None` в Python или `NULL` в базе данных — это слишком ленивое решение. Оно не объясняет причину, почему данных нет.
Отчества нет, потому что человек иностранец, или потому что мы забыли спросить?
Скидка равна `None`, потому что она ещё не посчитана, или потому что она равна 0%?
Разделение поля на значение и статус/мета-информацию (через `Enum` или числовые флаги) делает архитектуру прозрачной. Код становится самодокументируемым.

Я понял, что проектирование таблиц «в лоб», когда в одну сущность пихают 50 столбцов с `NULL`, - это признак плохой архитектуры. Вместо этого нужно использовать возможности самой СУБД:
- Декомпозировать таблицы (выносить редко заполняемые профили в отдельные связанные таблицы «один-к-одному» или «один-ко-многим»).
- Использовать специальные типы данных (например, `EMPTY` геометрию вместо `NULL` для координат).
