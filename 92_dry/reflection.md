# Принцип DRY -- не абсолютная истина

## Пример 1.

В проекте были два места c похожей формулой:

Расчёт скидки для постоянного клиента: `discount = price * 0.1 if price > 1000 else price * 0.05`
Расчёт бонуса для сотрудника: `bonus = salary * 0.1 if salary > 1000 else salary * 0.05`

Разработчик увидел дублирование формулы и создал универсальную функцию:

```python
def calculate_factor(value, high_threshold=1000, high_rate=0.1, low_rate=0.05):
    return value * (high_rate if value > high_threshold else low_rate)
```

К чему привело.
Через месяц:
- Скидку для клиентов изменили на прогрессивную шкалу (3 порога)
- Бонус сотрудникам привязали к KPI, а не к порогу зарплаты

Стало невозможно менять логику независимо. Пришлось разносить обратно, но зависимость уже была в 5 модулях. Потратили день на рефакторинг + поймали баг в расчёте зарплаты.


## Пример 2.

В парсере логов были два класса:
- LogParser — парсит строки вида 2025-01-01 ERROR msg
- CsvParser — парсит CSV

У них совпала логика пропуска пустых строк. Сделали базовый класс `BaseParser` с методом `_skip_empty_lines()`.

Через полгода:
- В логах появились пустые строки, которые нельзя пропускать (это маркер конца секции)
- В CSV пустые строки по-прежнему нужно пропускать

Пришлось добавить флаг `skip_empty_lines` в базовый класс, потом переопределять поведение в наследниках, потом сломали оба парсера.

```python
class BaseParser:
    def _skip_empty_lines(self, lines):
        return [line for line in lines if line.strip()]

class LogParser(BaseParser):
    def parse(self, lines):
        lines = self._skip_empty_lines(lines)
        # ...
```

Базовый класс раздулся условными операторами (`if self.skip_empties:`), нарушили LSP (подстановка сломала контракт). Переписали на композицию - каждый парсер сам решает, нужна ли фильтрация пустых строк.

## Выводы

Раньше я думал, что если вижу две одинаковые строчки кода — это сразу «плохо», и бежал выносить их в функцию. Теперь понимаю: одинаковый код ≠ одинаковое поведение в будущем. Два куска кода могут выглядеть похоже сегодня, но их смысл и требования к изменению - разные.

Вывод: буду задавать вопрос не «есть ли дублирование?», а «если я изменю логику в одном месте, должна ли она измениться в другом?». Если ответ «нет», то дублирование оправдано.

Меня учили: «абстрагируй, чтобы код был гибким». Но материал показал, что каждая абстракция - это:
- сложность понимания (нужно прыгать по файлам)
- риск «дырявости» (абстракция не скрывает детали полностью)
- новые зависимости (меняешь одно — ломается другое)

Теперь, когда хочется «убрать дублирование», я задаю себе вопросы:
1) Это буквально одинаковый код или просто похожий?
2) Изменение в одном месте почти всегда требует изменения в другом?
3) Могу ли я назвать новую абстракцию именем из предметной области? (не helper, utils, common)
4) Я уже вижу три использования?
5) Мне действительно нужна эта гибкость или я просто избегаю копипасты?

Если хотя бы на один вопрос ответ «нет», то оставляю дублирование. 

Главный вывод.
Не повторяться - плохая цель. Хорошая цель - сделать код понятным, легко изменяемым и надежным.
